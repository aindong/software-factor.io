# `softwarefactor requeue <run>` puts a stopped task back in the queue

## Goal

`softwarefactor requeue <run>` sets the task of a stopped or dropped run back to `queued`, so the next
`softwarefactor run` takes it in a new run on a new branch. The old run and its record are not touched. It refuses,
with a clear message and exit 1: a run that is still working or waiting, a run that ended done, and a task that is
already queued. Inside a run it is refused like the other commands that change the factory. The help and
`docs/operations.md` say so, and the operation is in the operations table.

## Choices (the task left these open)

- **How it decides.** Look the run up (none: `There is no run "<id>".`). Then by the run's status: `running` →
  "still working", `waiting` → "waiting for a person", `done` → "ended done". Only `stopped` and `dropped` go on.
  Then by the *task's* status: `queued` → "already queued"; `stopped` or `dropped` → requeue; anything else
  (`running`, `waiting`, `done`) means another run has taken the task since, and is refused ("another run").
  This keeps an old run's id from putting a task back in the queue under a newer run that is working or done.
- **The write is one statement**, `update tasks set status = 'queued' where id = ? and status in ('stopped',
  'dropped')`; if it changes no row, a run in another process got there first and the command refuses ("another
  run" wording). No transaction needed.
- **Nothing else is written.** No row of `runs`, `lane_runs`, `gate_results`, `inbox` or `events` is changed or added
  (no new event: the old record "stays as it is"). The new run comes from `softwarefactor run`, with a new id and a
  new branch, as for any task.
- **Where it lives.** `requeueRun(ws, runId): string` in `src/core/engine/stop.ts`, next to `stopRun` (same shape:
  open the db, look the run up, throw `UserError(message, fix)`, return the line to print). The CLI branch is next to
  `stop` in `src/cli.ts`. A missing run id is `"requeue" needs a run id.`, as `stop` words it.
- **Inside a run** needs no new code: `requeue` is not in `READ_ONLY` in `src/cli.ts`, so the existing check
  ("was started from inside a run") already refuses it. The test pins that. The agent guard
  (`FACTORY_COMMANDS` in `src/core/agents/guard.ts`) gets `"requeue"`, so an agent's shell call is denied too.
- **Output.** `run <id> requeued: the task "<title>" is queued, and the next softwarefactor run takes it.`
- **The operations table.** One operation, `runs_requeue`: `changes: true`, `cli: [["requeue", "<run>"]]`, input
  `z.strictObject({ run: runId })`, run by `command(at.root, ["requeue", input.run])` like `roles_bind` (the command
  ends at once; a refusal comes back as the command worded it, 409 in the API). The page, the API and the operator
  MCP server get it with no further code. The existing parity test needs an input for it in its `needs` map.
  No button in the interface: not asked for.
- **Docs.** `docs/operations.md`: a row in the table (`runs_requeue`, changes, `softwarefactor requeue <run>`) and a
  section "Putting a stopped task back in the queue" that says what it does and what it refuses, and that it is
  refused inside a run. `src/core/help.ts`: the line `requeue <run>  Put the task of a stopped or dropped run back
  in the queue`.
- **Not done:** requeue by task rather than by run, requeue of many runs, a flag to requeue a done run, an
  interface button.

## Acceptance criteria

1. Given a stopped run, when `softwarefactor requeue <run>` runs, then it exits 0, prints the run id and "requeued",
   and the task's status is `queued`. The run's row and its `lane_runs` rows are identical to what they were.
2. Given the same, when `softwarefactor run` follows, then there are two runs of the one task (no second task), the
   new one has another id and another branch, and the old run's record is still identical.
3. Given a dropped run, `requeue` exits 0 and the task is `queued`; the run row is unchanged.
4. Given a task that is already queued (requeued once), `requeue <run>` exits 1 with an `error:` line saying
   "already queued", and the task stays queued.
5. Given a run that waits for a person, `requeue` exits 1 with an `error:` line that says it is waiting; the task is
   unchanged.
6. Given a run that is still working, `requeue` exits 1 with an `error:` line saying "still working"; the task and
   run are unchanged.
7. Given a run that ended done, `requeue` exits 1 with an `error:` line saying "done"; the task stays `done`.
8. Given a stopped run whose task has been taken by another run since (task `running`), `requeue` exits 1 with an
   `error:` line saying "another run"; the task is unchanged.
9. Given an unknown run id, `requeue` exits 1 with `There is no run "<id>".`; given no run id, exit 1 with
   `needs a run id`.
10. Given `FACTOR_RUN_ID` in the environment, `requeue` exits 1 with "inside a run" and changes nothing.
11. Given the operations table, `runs_requeue` is there as a change with `cli [["requeue", "<run>"]]`; through the
    interface's API it requeues (200, `said` has "requeued"), refuses an unknown run and an already queued task (409
    with the command's words) and a malformed run id (422); the operator MCP server does the same.
12. Given the help and `docs/operations.md`: the help has the `requeue <run>` line; the operations table has the
    `runs_requeue` row; the doc has the section and, in it, "stopped", "dropped", "queued", "new branch", "still
    working", "waiting", "done", "already queued", "inside a run" and "exit 1".
13. Given the agent guard, an agent's call of `softwarefactor requeue <run>` (also through `npx`) is denied.
14. Given the rest of the suite, nothing else changes: `operations-parity` (with the new operation in its `needs`
    map), `run-stop`, `ui-inbox` and the rest still pass; `pnpm typecheck` and `pnpm lint` are clean.

## Risks / out-of-scope

- A `softwarefactor run` in another process may claim the task between the check and the write: the conditional
  update refuses then instead of overwriting.
- A dropped run's worktree was removed when it was dropped; a stopped run's worktree and branch stay for the person
  to look at. Requeue touches neither; the new run has its own.
- A done task whose run is old cannot be requeued: by design, the task asks for a stopped or dropped run.
